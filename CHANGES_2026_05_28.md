## Living Whitelist + Regime-Aware Candidates (2026-05-28 sessao 2)

### Item 1 — Regime-aware tier_level (lib_quant_whitelist.ps1)

**O que foi feito:**
- Adicionado parametro `-RegimeProvider` (scriptblock opcional) a `Merge-QuantWhitelistIntoCandidates`.
- Quando fornecido, o provider e chamado para cada ativo forcado da whitelist estatica.
- Se o regime retornado for `BEAR_STRONG` ou `BEAR_WEAK`, o `tier_level` e rebaixado de 1 para 3.
- Regimes `BULL_*`, `SIDEWAYS`, `TRANSITION`, ou `$null` mantem o `tier_level` original.
- Adicionada funcao `Get-MarketRegimeFromCache` que le `journal/regime_state.json` e retorna o regime para o market pedido, ou `$null` se arquivo ausente ou market nao encontrado. Fail-soft total.
- Em `scripts/scan_master.ps1`, a chamada a `Merge-QuantWhitelistIntoCandidates` agora passa `-RegimeProvider { param($m) Get-MarketRegimeFromCache -Market $m }` quando a funcao estiver disponivel.

**Por que:**
O problema original era que todos os ativos da whitelist estatica em regime BEAR monopolizavam os slots do orchestrator com `tier_level=1` e `score=100`, impedindo qualquer trade organico de passar. Com o rebaixamento para `tier_level=3` em regime BEAR, os candidatos organicos do scanner voltam a competir pelos slots.

**Impacto esperado:**
Em ciclos de mercado BEAR, os ativos da whitelist estatica deixam de bloquear o pipeline. O sistema passa a executar trades em candidatos organicos com melhor momentum atual, enquanto os ativos da whitelist permanecem monitorados (tier 3) prontos para voltar ao topo quando o regime mudar.

### Item 2 — Living Whitelist conectada ao cron semanal (promotion_weekly_cron.ps1 + lib_living_whitelist.ps1)

**O que foi feito:**
- Adicionada funcao `Get-LivingWhitelistMetrics` em `agents/lib_living_whitelist.ps1`.
  - Recebe `$Market`, busca closes diarios via CoinEx API, chama `Compute-AssetRegime`.
  - Retorna hashtable com `regime_asset`, `regime_btc`, `mom_20d`, `sharpe_30d=0`, `n_trades=0`.
  - Fail-soft: qualquer erro (API indisponivel, historico insuficiente) retorna defaults com `regime_asset="UNKNOWN"`.
- Em `scripts/promotion_weekly_cron.ps1`:
  - Adicionado dot-source de `lib_quant_whitelist.ps1` (para `Get-MarketRegimeFromCache`).
  - O bloco de Living Whitelist scan agora usa `Get-LivingWhitelistMetrics` como provider primario (mais leve, so busca daily closes). Fallback para `Build-MetricsProvider` se a funcao nao estiver disponivel.

**Por que:**
O `promotion_weekly_cron.ps1` ja tinha o bloco de Living Whitelist scan mas usava `Build-MetricsProvider` (que busca candles 4h + daily + paper backtest — pesado). Para o scan de discovery semanal, o regime diario e suficiente. `Get-LivingWhitelistMetrics` e mais rapido e fail-soft, adequado para varrer 30+ ativos sem timeout.

**Impacto esperado:**
O cron semanal agora descobre automaticamente ativos `BULL_STRONG` no universo CoinEx e os promove para `OBSERVATION` sem intervencao manual. O scan e mais rapido e resiliente a falhas de API.

### Contexto

Análise dos logs revelou dois problemas distintos no tratamento do beta cap:

### Fix 1 — Regra anti-hallucination beta (lib_mentor_rules.ps1 + mentor_agent.ps1)

**Arquivos alterados:**
- `agents/lib_mentor_rules.ps1` — regra 6 adicionada em `Get-MentorAntiHallucinationRules`
- `agents/mentor_agent.ps1` — regra 5 adicionada em `MENTOR_DEBATE_SYSTEM`

**Regra adicionada:**

## Evolução 4b — DSR Forbidden Phrases Guard (2026-05-28 sessão 5)

### Problema identificado

Análise dos logs do dia revelou que o LLM do Mentor usava `n_trades=0` como
**razão de ABORTAR** em praticamente todos os ciclos, mesmo com três camadas
de proteção já existentes:

- `[DSR_HISTORY]` marcado como `[INFO-ONLY: nao bloqueia]` no gate block
- Regra 5 explícita no `lib_mentor_rules.ps1`: "n_trades=0 NAO impede trade"
- `lib_mentor_gate_block.ps1` com comentário "INFORMATIVO apenas"

**Exemplos reais dos logs (28/05):**
```
XMRUSDT: DSR n_trades=0 com dsr=0.5 e track record zerado neste ativo
BCHUSDT: DSR n_trades=0 com dsr=0.5 e track record inexistente neste ativo
SKYUSDT: DSR n_trades=0 significa zero track record validado neste ativo
RENDERUSDT: DSR n_trades=0 + ALPHA_HIST ABSENT = zero track record validado
```

O guard pós-resposta (`Test-PromptForbiddenPhrases`) **não detectava** essas
violações porque as frases DSR não estavam na lista `MENTOR_FORBIDDEN_PHRASES`.
O LLM ignorava a instrução textual e usava DSR como veto de facto.

### Causa raiz

O problema é de **enforcement**, não de instrução. A regra existia no system
prompt mas não havia mecanismo de detecção automática da violação na resposta.
O guard já funcionava para `"Mesa pulou"` e `"FQS indisponivel"` — faltava
estender o mesmo padrão para as frases DSR.

### O que foi feito

**`agents/lib_mentor_gate_block.ps1`** — 9 frases adicionadas à
`MENTOR_FORBIDDEN_PHRASES`:

| Frase | Padrão que captura |
|---|---|
| `"track record inexistente"` | "track record inexistente neste ativo" |
| `"track record zerado"` | "track record zerado impede aprovacao" |
| `"zero track record"` | "zero track record validado" |
| `"sem track record"` | "sem track record validado/neste ativo/etc" |
| `"DSR n_trades=0"` | "DSR n_trades=0 com dsr=0.5 e..." |
| `"n_trades=0 e track"` | "n_trades=0 e track record inexistente" |
| `"n_trades=0 elimina"` | "n_trades=0 elimina qualquer edge historico" |
| `"n_trades=0 significa"` | "n_trades=0 significa zero track record" |

**Nota de design:** `"track record validado"` (afirmativo) foi **excluído**
intencionalmente — seria falso positivo em contextos legítimos como
`"track record validado por 15 trades confirma edge"`. A negação já é coberta
por `"sem track record"`.

**`agents/lib_mentor_rules.ps1`** — Regra 5 expandida com lista explícita
de frases proibidas no system prompt do LLM:

```
FRASES PROIBIDAS (violacao = decisao invalida):
  - "track record inexistente", "track record zerado", "zero track record"
  - "sem track record", "DSR n_trades=0", "n_trades=0 elimina/significa/e"
Essas frases transformam dado informativo em veto -- comportamento incorreto.
```

| CAOS genuíno (1/1/1 split) | 95 |
| Padrão dominante | SHORT/NEUTRO/LONG — 51.6% dos CAOS |
| LIDAR vota NEUTRO no CAOS | 38.9% |
| LIDAR vota oposto ao Termal | 57% dos casos |

**Causa raiz:** O LIDAR estava **inferindo direção** pelo contexto técnico em vez de confirmar o `direction_proxy` do setup. Exemplos reais:
```
RENDERUSDT: RR=5, vol_ratio=1.21, liquidez OK → LIDAR vota LONG (Termal=SHORT)
SUIUSDT:    RR=5, vol_ratio=1.8,  liquidez OK → LIDAR vota LONG (Termal=SHORT)
```
O prompt dizia `"Leia o campo direction_proxy"` — instrução fraca que o LLM ignorava.

**Problema secundário:** threshold `vol_ratio >= 0.5` muito alto para mercado BEAR onde volume é sistematicamente baixo. P25 dos casos de CAOS = 0.22.

### O que foi mudado

**`agents/mesa_agent.ps1`** — `$MESA_LIDAR_SYSTEM` reescrito com:

1. **Instrução imperativa** — `"REGRA ABSOLUTA"` + `"NUNCA vote em direcao diferente do direction_proxy"`
2. **Algoritmo numerado** — 4 passos explícitos que o LLM deve seguir
3. **Exemplos corretos e errados** — casos concretos com `direction_proxy=SHORT → sinal=SHORT` e o que é ERRADO
4. **Threshold vol_ratio: 0.5 → 0.37** — baseado nos dados (P25=0.22 nos CAOS, 0.37 é conservador)
